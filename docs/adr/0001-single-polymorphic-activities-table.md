# Single polymorphic `activities` table for Contact and Deal timelines

Both Contacts and Deals need a mixed timeline of system events (deal stage changes) and user Comments, and deal stage-change history can't be reconstructed after the fact since `deals.stage` only stores the current value — so events must be persisted as they happen. We chose one shared `activities` table (`entity_type`, `entity_id`, `type`, `created_at`, plus per-type columns — `body`/`author_email` for a Comment, `from_stage`/`to_stage` for a stage change, enforced by a check constraint) queried per entity, over separate `comments` and `deal_stage_changes` tables, so a single query renders a full timeline and any new entity or event type added later is just a new `type` value rather than a new table.
